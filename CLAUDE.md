# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Marketing/e-commerce site for ВФД (Владимирская фабрика дверей) — a door & aluminum-partition showroom in Chelyabinsk (`vfd74.ru`). Astro 6 + Vue 3 islands + Tailwind v4, content and product data primarily in Russian. Statically built and rsync-deployed to a bare-metal VPS.

## Commands

```bash
npm run dev       # astro dev — local dev server
npm run build     # astro build — static build into dist/
npm run preview   # preview the production build locally
npm run gen:renders  # regenerate public/renders/alum-covers/*.webp from public/media originals (see scripts/gen-render-gallery.mjs)
npm run media:sync   # localize new cloud URLs / Supabase photos into public/media, then make their thumbnails (see Images / media below)
npm run gen:model-thumbs  # only thumbnails of catalog photos: public/renders/models/<path>-320|640.webp (idempotent; -- --force rebuilds all)
npm run gen:responsive    # srcset variants for hero slides, home promo sliders, category cards, plinth scheme (scripts/gen-responsive.mjs)
npm run media:check  # verify every /media/... referenced by src + DB exists on disk
npm run deploy    # git push production main — DO NOT run unless the user explicitly asks
```

There is no test runner or linter configured in this repo. `tsconfig.json` extends `astro/tsconfigs/strict`; rely on `astro check` / editor TS diagnostics for type issues, and `npm run build` as the main correctness gate (it runs `getStaticPaths` against the live Supabase project, so a broken query fails the build).

## Deployment — never run automatically

Deploys go out via `git push production main` to a `post-receive` hook on a Beget VPS (see `deploy/post-receive`, `deploy/setup-server.sh`): it checks out `main`, runs `npm ci && npm run build`, then `rsync`'s `dist/` to the nginx web root. **Do not push to the `production` remote or run `npm run deploy` unless the user explicitly asks in that turn.** Default to local build/preview only.

## Server (nginx)

Конфиг nginx лежит в `deploy/nginx/` (`vfd74.ru.conf` + `vfd74-perf.conf` — кеш-заголовки одной переменной, Brotli, HSTS), порядок применения — в `deploy/nginx/README.md`. `git push production` его **не** меняет: конфиг ставится на сервер вручную, поэтому правки в репозитории не действуют, пока их не применили.

## Architecture

**Rendering model**: Astro pages are server/build-time rendered (mostly static, with `getStaticPaths` for dynamic routes). Interactivity lives in Vue 3 "islands" mounted with explicit `client:*` directives (`client:only="vue"`, `client:load`, `client:visible`, `client:idle`) — pick the directive based on how critical-path the component is (e.g. `Header`/`Footer` use `client:only="vue"` to avoid hydration mismatches; below-the-fold sections use `client:visible`/`client:idle`).

**Data sources** — two distinct patterns, don't mix them up:
1. **Supabase-backed catalog** (`src/lib/supabase.ts`, requires `PUBLIC_SUPABASE_URL`/`PUBLIC_SUPABASE_ANON_KEY` in env): the main door catalog (`src/pages/catalog.astro`, `src/pages/models/[id].astro`) queries the `model_colors` table with nested joins to `colors → coatings` and `models → series → coatings`. Pages fetch all data server-side at build time (photo URLs go through `resolveMedia` → local `/media/...`), normalize into a flat `CardItem`/`CatalogCardItem` shape (one card per model, first color picked, hex colors normalized for a `С`/`C` Cyrillic-Latin typo seen in the DB), then hand the flat array to a Vue island (`CatalogClient.vue`) which owns all filtering/sorting/pagination/URL-query-sync client-side — there is no server round-trip for filtering.
   - Model pages and the Yandex product feed (`src/pages/feed/yandex.xml.ts` → `/feed/yandex.xml`, YML for Яндекс Товары) share one data source, `src/lib/model-entries.ts`, and one naming/description module, `src/lib/product-text.ts`. Yandex checks feed price/photos against the page, so change prices, photos or names there — never compute them separately in the page or the feed.
2. **Static TypeScript data modules** (`src/data/*.ts`): standalone product lines that aren't in Supabase yet — e.g. `skrytye-dveri-products.ts` (hidden/flush doors — sizes, pricing tiers, `calcCustomPrice`), `partitions.ts` (aluminum partitions), `door-categories.ts` (SEO landing-page content keyed by `slug`, rendered through the generic `DoorCategoryLanding.astro` template), `accessories.ts`, `series-descriptions.ts`. These pages are otherwise fully static/content-driven.

**Images / media**: everything is local — nothing is loaded from Yandex Cloud at runtime or at build time (the cloud had mass outages). All product photography, schemes and videos live in `public/media/<path>` and are served as `/media/<path>`; the layout mirrors the old bucket paths (`https://storage.yandexcloud.net/<bucket>/<path>` → `/media/<path>`, both buckets merged — no path collisions), top-level folders are the sections (`works_prod/` portfolio, `metal_doors/` entrance doors, `emalex/`, `emal/`, `innova/`, `Smart/`… catalog colors, `alum_*` partitions, `invisible/` hidden doors, `statya/` articles, `video/`). Pre-resized derivatives for cards/thumbs live in `public/renders/**` (generated by `scripts/gen-*.mjs` from `public/media` via `scripts/lib/media.mjs`; the generators exist because Astro's remote-image optimizer is slow/no-cache — see the comment atop `scripts/gen-render-gallery.mjs`). Rules:
- **Never write `https://storage.yandexcloud.net/...` in `src/`.** Reference `/media/...` paths. The shared path rule is `src/lib/media-path.mjs`.
- **Adding new content**: upload the photo to the cloud as before, paste its cloud URL into the data file/article, then run `npm run media:sync` — it downloads the file into `public/media`, rewrites the URL to `/media/...` in `src/` and `astro.config.mjs`, and tops up Supabase photos. Commit `public/media` together with the code. If the new content has previews (portfolio cover, article images), then also re-run its `gen:*` script (portfolio: `gen:portfolio-thumbs` — makes `<id>.webp` 1080w and `<id>-640.webp` for the home rail `PortfolioPreview.astro`; articles: `node scripts/gen-article-images.mjs` — without it new images still work, just load the heavy originals).
- **Supabase photos** (`model_colors.photo_url`) stay as cloud URLs in the DB (the admin uploads there); at build `src/lib/media-resolve.ts` swaps them for the local `/media/...` file, and falls back to the cloud URL with a `[media]` warning if the file isn't synced yet. `media:sync` also downloads them.
- **Absolute URLs**: pages emit relative `/media/...`; `og:image` and JSON-LD are made absolute in `BaseLayout.astro` (`absolutizeAssets`), the Yandex feed and sitemap images do the same. Don't hand-build `https://vfd74.ru/media/...` strings elsewhere.
- **Integrity checks**: `npm run build` runs `postbuild` → `scripts/sync-media.mjs --dist`, which fails if any `/media/...` referenced by the built site is missing on disk. `npm run media:check` does the same for sources + DB without building.
- **Скорость картинок** (замеры Lighthouse: ширина экрана телефона ~380 CSS px, оригиналы 1100–1900 px):
  - крупные фото — только `<img>` с `srcset`/`sizes` и `loading="lazy"`, не CSS `background-image` (фон браузер грузит сразу, без ленивой загрузки);
  - слайдеры (`HeroSlider.vue`, `PhotoAutoplaySlider.vue`) кладут все слайды в DOM, поэтому `src` у неактивных слайдов задаётся лениво — иначе `loading="lazy"` не срабатывает (картинки «в зоне видимости») и грузятся все сразу;
  - ресайзы 640w/960w для слайдов, промо-слайдеров, карточек «Каталог» на главной и схемы плинтуса делает `npm run gen:responsive` (`scripts/gen-responsive.mjs`, список `JOBS`); новая картинка в таком месте → строка в `JOBS` + `srcset` в компоненте. Картинки статей и портфолио — свои `gen:*`, для страниц каталога подходит `articleImg()` из `src/lib/article-images.ts`;
  - **эскизы фото моделей**: `/media/<путь>.webp` → `/renders/models/<путь>-320.webp` и `-640.webp` (3–9 КБ вместо 14–45 КБ). Делает `scripts/gen-model-thumbs.mjs` из фото `model_colors` (входит в `npm run media:sync`, идемпотентен); `srcset` строит чистая функция `thumbSrcset()` из `src/lib/model-thumbs.mjs` (её же использует Vue-карточка `CatalogProductCard.vue` и `RelatedModels.astro`). Нет эскиза у фото (новый цвет, не запускали `gen:model-thumbs`) — `catalog-data.ts` ставит `noThumb`, карточка берёт оригинал и в логе сборки предупреждение `[media] нет эскиза`; ссылка в `dist` на несуществующий эскиз роняет `postbuild`. Эскизы коммитятся вместе с `public/media`;
  - **CLS**: остров `client:only` пуст до загрузки JS, а потом раздвигает страницу (на страницах серий это давало CLS 0,19). Карточки `InfoImageViewer` с `client:only` ставь через `components/catalog/InfoImageViewerIsland.astro` — он кладёт в слот `fallback` пустой блок высотой в готовую карточку (формула — по стилям `InfoImageViewer.vue`, при их правке обнови её). Запасные шрифты `Rubik Fallback`/`Manrope Fallback` в `global.css` подогнаны по метрикам (`size-adjust`, `ascent-override`), чтобы подмена шрифта не перестраивала строки; цифры считаются fontTools по файлам из `public/fonts`;
  - `preloadImage` в `BaseLayout` с `preloadImageSrcset` обязан иметь тот же `sizes`, что у самого `<img>` (`preloadImageSizes`), иначе браузер скачает картинку дважды.
- Files keep the exact key from the cloud, including odd names (spaces, parentheses) — don't rename; refs are percent-encoded by the browser.

**Reviews** (`components/home/Reviews.astro`, data `src/data/reviews.ts`): static Astro, text only (no client photos). Cards share the row height; author sits at the bottom; text size by length (≤110 chars — large quote, >260 — clamped to 7 lines, «Читать полностью» opens a native `<dialog>`). Horizontal rails («Отзывы», «Фотоотчёты») share one kit: `.rail`/`.rail-scope` in `global.css` (column width via `--rail-col`, `--rail-col-md`, `--rail-col-lg`), `components/ui/RailControls.astro` (arrows + «Все …» link, loads `src/lib/rail.ts` once per page) and `components/ui/RailEndCard.astro` (graphite last card). Section needs `data-rail-scope`, list `data-rail`.

**Home products**: «Новинки» (Техно, Штрих 2А, «Рефлекс») — one tabbed block `components/home/Novelties.astro`; «Секрет» is not a novelty and has its own block «Скрытые двери из наличия…» below the measure band. Both render through `components/home/ProductFeature.astro`; «Каталог» (`CatalogCategories.astro`, three photo tiles, header via `components/home/SectionHeader.astro` — H2 left, lead right) are static Astro, mobile/tablet tile reveal via `src/lib/tile-reveal.ts` + `data-tile-reveal`/`data-reveal-*` attributes (styles at the end of `global.css`; never translate the stretched-link `<a>` — it breaks CLS); data in `src/lib/home-promos.ts` (`getHomePromos()` → `{ novelties, inStock }`, prices live — catalog via `getCatalogCards`, hidden doors via `skrytye-dveri-products.ts`). New novelty = new object in `novelties`, not a new component. All panels are in the static HTML; inactive ones are `hidden`, so their photos and slider island (`PhotoAutoplaySlider`, 8 s, autoplays only on screen) load only when the tab is opened. Short data texts go through `typograph()` (`src/lib/typograph.ts`) — no line starting with «—», no hanging prepositions, «500 ₽» unbroken. Wording: двери «в покрытии Эмалекс», not «на покрытии».

**Maps**: no Yandex iframe/screenshot. The salon map is our own vector map of the surroundings built from OpenStreetMap (`scripts/gen-visit-map.mjs` → `src/data/visit-map.json`; rendered by `src/lib/salon-map.ts` into `/salon-map-dark.svg` for the footer and `/salon-map-light.svg` for `/contacts/`, see `src/pages/salon-map-*.svg.ts`). Re-run the generator only if `address.coordinates` in `contacts-data.ts` changes; keep the «© участники OpenStreetMap» credit next to the map. Route buttons still open Yandex Maps.

**Blog articles** (`src/content/articles/*.mdoc`, Markdoc; schema in `src/content.config.ts`):
- `publishDate` is the **real** publication date — never backdate it (the page, JSON-LD `datePublished` and sitemap `lastmod` all use it). Publication is scheduled by that date: the site is static, so an article with a future date is simply not generated (no page, no sitemap entry, not on the home page, not in «Читайте также»/«Статья по теме») until a build runs on or after the date — i.e. any `git push production main` that day or later. **Always read articles through `getPublishedArticles()` from `src/lib/articles.ts`, never `getCollection('articles')` directly.** Preview scheduled articles with `npm run dev` (shows all) or `ARTICLES_PREVIEW=1 npm run build`.
- Markdoc tags (`markdoc.config.ts`): `figure`, `callout`, `cards`/`card`, `photogrid`/`photo`, `coatingPrices`, `linePrices of="hidden"|"thermo"` (live «от» prices from the catalog data modules — don't hardcode prices in text), `ifpublished to="slug"` (renders its content only once that article is published — use it for links/sentences pointing at a not-yet-published article). Optional frontmatter `related: [slugs]` curates «Читайте также»; the table of contents is built from H2 headings automatically.
- Catalog/section pages link to articles with `<RelatedArticleCard slugs={[...]} asSection />` (shows only published ones). After adding an article or its images run `npm run gen:article-images`; images follow the `/media/...` rules above.
- Facts in article text must come from the site's own data (specs, FAQ, process, portfolio) — check the data modules before stating a number, and prefer `linePrices`/`coatingPrices` over typed prices.

**SEO infrastructure** is load-bearing, not incidental:
- `BaseLayout.astro` centralizes `<head>` (OG/Twitter meta, canonical, favicons, JSON-LD via `structuredData` prop, font preloads, Yandex Metrika, the ФЗ-152 cookie-consent banner).
- `astro.config.mjs` wires `@astrojs/sitemap` with custom `serialize()`/`filter()` — priority/changefreq rules and `/privacy` exclusion are intentional, keep them when adding routes.
- Landing pages under `/catalog/<slug>` follow the `DoorCategory` data shape in `door-categories.ts` + `DoorCategoryLanding.astro` template; adding a new SEO-targeted category landing page means adding a data object there, not a new bespoke `.astro` file, unless the page needs a real product grid (Supabase-backed) rather than static content.

- **`<title>` ≤ ~70 знаков** (дальше выдача обрезает). Модели: `productTitle()` в `src/lib/product-text.ts` сама укорачивает заголовок по «лесенке» (`productName` для фида не трогаем). Серии — то же в `catalog/series/[slug].astro`. Портфолио и статьи: необязательное поле `seoTitle` (в `PortfolioWork` и во frontmatter статьи) — короткий `<title>` без бренда (` | ВФД` добавляется сам), H1 остаётся полным `title`. У нового длинного заголовка заводи `seoTitle`.
- **Сквозная перелинковка**: Header/Footer — `client:only`, в статическом HTML их нет, поэтому серверный блок «Разделы сайта» (`components/layout/SiteLinks.astro`, ставится в `BaseLayout`) даёт каждой странице прямые ссылки на все разделы и лендинги. Данные — `src/lib/site-links.ts` (лендинги по покрытию/цвету/стилю берутся из `door-/color-/style-categories.ts` сами; скрытые двери и «О салоне» — списками в этом файле). Новая страница верхнего уровня или новый сценарий скрытых дверей → добавь в `site-links.ts`. «Смотрите также» между лендингами — `components/ui/RelatedLinks.astro` + `relatedLandings()`. Страницы моделей: блок «Другие модели серии» (`components/catalog/RelatedModels.astro` + `lib/related-models.ts`) — окно из 8 соседей по цене в той же серии, детерминированно; каждая модель получает ≥4 входящих ссылок. Данные — те же `ModelEntry`, что у страницы и фида.
- **Аналитика (Яндекс Метрика, счётчик 106993554)**: цели-JS-события шлёт делегированный обработчик кликов в `components/analytics/YandexMetrika.astro` (только в PROD). Идентификаторы: `phone_click` (tel:), `email_click` (mailto:), `telegram_click`, `vk_click`, `max_click`, `whatsapp_click`, `route_click` (короткая ссылка `yandex.ru/maps/-/…` на карточку салона), `review_platform_click` (2ГИС / поиск Яндекс Карт). Цель должна быть заведена в интерфейсе Метрики (Цели → JavaScript-событие) с тем же идентификатором, иначе событие не засчитается. Новый тип контактной ссылки → добавь строку в `GOALS`.

**Styling**: Tailwind v4 is loaded via `@tailwindcss/vite` (no `tailwind.config.*`); design tokens are declared with `@theme` in `src/styles/global.css` (e.g. `--color-ink`, `--color-body`) and consumed as Tailwind utilities (`text-ink`, `bg-ink`). Page-specific CSS (e.g. `src/styles/partitions.css`) is imported directly by the page that needs it. Headings use the type roles from `global.css`: page H1 — `.t-h1`, section H2 — `.t-h2` (one size for every section on a page; no ad-hoc `text-3xl md:text-5xl`), card titles — `.t-h3`. No small labels above headings (eyebrows were removed site-wide) — say status/context in the heading or text.

**Legal/company data**: `src/lib/contacts-data.ts` holds the legally-required business info (ИП reqisites, address, hours, phones) used across contacts, footer, and structured data — update once, not per-component.
